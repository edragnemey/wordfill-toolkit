# 技术方案数据填写

你只做一件事：**产出一份数据 JSON**，结构以 `assets/技术方案数据骨架.json` 为准，每个字段的内容按下面的字段契约和对话上下文来写。

## 这个 skill 是自包含的

所有要用的文件都在本 skill 目录里，整个文件夹拷到别的电脑也能直接用：

- `assets/技术方案数据骨架.json` — JSON 结构样板（键名、层级、表格列）
- `assets/技术方案数据骨架_字段说明.json` — 每个字段填什么的说明（字段契约）
- `assets/技术方案模板示例.docx` — 配套 Word 模板（已打包，生成文档直接用）
- `scripts/wf.py` + `scripts/wordfill/` — 校验与填充引擎（自带，不用另装工具）
- `references/*.md` — JSON 写法与填写规则

运行环境：Python 3.10 以上 + `python-docx`（`pip install python-docx`）。
填充引擎已经打包在 `scripts/` 里，**不需要**另外安装工具或依赖别的 skill。
换机器后先跑一次环境自检：`python scripts/env_check.py`。

## 字段契约（唯一权威）

| 字段 | 类型 | 填写要求 |
| --- | --- | --- |
| `改造清单` | 表格 | 每个需要改造的工程/类/方法一行；没有的不要凑数；列说明：工程：工程名，如 dceppay；模块或类：类名或模块名，取真实代码里的名字；改造说明：本处改了什么，一句话；接口名、方法名原样保留；类型：新增 / 修改 / 删除 |
| `字段清单` | 表格 | 本次数据库变更涉及的字段，每个字段一行；没有数据库变更时给空数组；列说明：表名：物理表名；字段：字段英文名；类型：字段类型，如 varchar(16)；默认值：默认值；没有默认值写 NULL；说明：字段用途，一句话 |
| `接口清单` | 表格 | 对外新增或调整的接口，每个接口一行；列说明：接口名：接口名或方法名；方法：HTTP 方法 / RPC 方法，如 POST；说明：接口作用一句话；类型：新增 / 修改 |
| `需要数据库变更` | 是/否 | true 或 false：本次是否涉及建表改表 |
| `需要停机` | 是/否 | true 或 false：上线是否需要停机窗口 |
| `方案名称` | 文本 | 本次技术方案的名称，取用户这次需求的标题，不加“关于……的” |
| `文档编号` | 文本 | 项目内文档编号，如 TS-2026-0917；不知道就写【待确认：文档编号】 |
| `版本` | 文本 | 版本号，如 V1.0；首次编写写 V1.0 |
| `编制人` | 文本 | 编写人姓名，来自用户或团队约定；没有就写【待确认：编制人】 |
| `编制日期` | 文本 | 编写日期，格式 YYYY-MM-DD |
| `评审状态` | 文本 | 如 待评审 / 已评审 |
| `需求来源` | 文本 | 需求来源部门或需求单号 |
| `需求背景` | 文本 | 1-2 段：现状是什么、存在什么问题、为什么改；用工程文档书面语 |
| `改造目标` | 文本 | 一句话说明改造后达到什么状态，可含范围边界 |
| `涉及工程` | 文本 | 本次改造涉及的应用/工程名，多个用顿号分隔 |
| `sql_for_database_modification` | 文本 | 建表/改表 SQL，原样保留缩进，多条语句用 \n 分隔 |
| `停机窗口` | 文本 | 需要停机时填写，如 2026-09-20 02:00-04:00；不需要停机可空 |
| `回滚方案` | 文本 | 出问题时如何回滚，一句话 |
| `测试要点` | 文本 | 测试需要覆盖的点，每条一行，用 \n 分隔 |
| `风险` | 表格 | 本次改造的风险点，每条一行；内容与应对都要具体；列说明：内容：风险描述；应对：应对或缓解措施 |

完整说明见 `assets/技术方案数据骨架_字段说明.json`。**不要**为了搞清楚字段含义去分析 Word 模板或猜结构——契约里写的就是全部要求。

- **表格字段（按行增加，列名不要改）**：`改造清单`、`字段清单`、`接口清单`、`风险`
- **必须填**：`需要数据库变更`、`需要停机`、`方案名称`、`文档编号`、`版本`、`编制人`、`编制日期`、`评审状态`、`需求来源`、`需求背景`、`改造目标`、`涉及工程`、`sql_for_database_modification`、`回滚方案`、`测试要点`
- **可空/选填**：`停机窗口`

## 怎么填

1. 契约里写明"取什么、从哪取"的，严格照办，不要自由发挥。
2. 对话、附件、代码里已经出现的技术名词（表名、字段名、接口名、类名、SQL）原样搬进 JSON，不改写。
3. 背景、目标、影响、测试要点这类描述性内容，用上下文里的事实组织成工程文档口吻；不要口号、套话，不要编数字和结论。
4. 没有依据的事实类内容（人名、日期、版本号、金额、数量、SQL）写 `【待确认：xxx】`，并在回复里说明还差什么。
5. 缺信息时一次最多问 3 个关键问题，其余用【待确认】占位，先把可用初稿交出去。

通用填写规则见 [references/how-to-fill.md](references/how-to-fill.md)，JSON 写法（格式修饰符、表格、循环、条件、图片）见 [references/json-rules.md](references/json-rules.md)。

## 表格 / 数组字段

- 表格字段按行增加：每个对象一行，列的键名与契约一致，不要自己改列名。
- 行数由真实内容决定，不凑数、不留空行；一行内容都没有时给空数组 `[]`，并在回复里说明。
- 表头顺序、列宽、列格式、合并列按契约里的写法给，例如
  `"表头": {"表名": "4cm", "字段": "3.1cm"}, "合并列": ["表名"]`。
- 多行文本（SQL、代码、多条说明）用 `\n` 换行。

## 校验与交付

```
# 结构校验（不需要 Word 模板）
python scripts/wf.py check --keys-from "assets/技术方案数据骨架.json" "数据.json" --config "assets/技术方案数据骨架_字段说明.json"
# 用自带的 Word 模板生成文档
python scripts/wf.py fill "assets/技术方案模板示例.docx" "数据.json" -o "结果.docx" [--pdf]
```

`check` 退出码为 0 才算完成：缺键、空值、表格结构不对都会被报出来。
交付时用一两句话说明每个字段的来源（上下文 / 附件 / 代码 / 推断 / 待确认），不要把全文贴进回复。

## Word 模板

模板已经打包在 `assets/技术方案模板示例.docx`，生成数据后用上面第二条命令出文档；模板本身不需要分析。用户另外指定模板时，把路径换成那个文件即可。
