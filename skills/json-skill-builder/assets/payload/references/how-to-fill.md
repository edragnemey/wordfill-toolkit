# 字段填写配置：每个字段填什么

字段填写配置就是这个 skill 的**契约**：它决定了要产出哪些键、每个键填什么。有了它，你不需要看 Word 模板也能完成工作。

有配置时严格按配置填；没有配置时按 JSON 骨架里的字段名推断，并在交付时说明推断依据。

## 1. 配置的格式

### 推荐：与数据同构的说明文件

结构和数据 JSON 一模一样，只是叶子节点写"这里填什么"。读起来直观，也方便直接对照：

```json
{
  "prd_name": "需求/方案名称，取用户这次需求的标题",
  "prd_short_description": "一到两句话概括本次改造的目标和范围，60 字以内",
  "字段清单": {
    "_行说明": "本次数据库变更涉及的字段，每个字段一行；没有数据库变更就写空数组",
    "表名": "变更涉及的物理表名",
    "字段": "字段英文名",
    "类型": "字段类型，如 varchar(16)",
    "默认值": "默认值；没有默认值写 NULL",
    "说明": "字段用途，中文一句话"
  },
  "sql_for_database_modification": "建表/改表 SQL，多条语句用 \\n 分隔，保留缩进",
  "code_description": "代码改造点，每条一行，用 \\n 分隔"
}
```

### 也可以：带元信息的配置

需要区分必填、来源、示例时用这种写法：

```json
{
  "prd_name":  { "_说明": "需求名称", "_来源": "对话标题", "_必填": true, "_示例": "商户信息管理优化需求" },
  "变更影响":  { "_说明": "对现有功能的影响", "_来源": "上下文或代码分析", "_必填": false }
}
```

下划线开头的键只是说明，不会进入数据 JSON。

## 2. 拿不到配置时怎么办

1. 用户手里通常已经有 JSON 骨架或历史数据文件 —— 直接照它的键填，键名本身就是线索
   （`sql_for_database_modification`、`code_description`、`字段清单`）。
2. 只有 Word 模板时，跑一次 `wf.py skeleton 模板.docx -o 数据.json` 拿键名，**不要**手工分析模板。
3. 还判断不了含义的，按"能不能影响文档正确性"决定：影响 → 问用户（一次最多 3 个）；不影响 → 用【待确认】占位并继续。

## 3. 内容从哪来

| 来源 | 用法 |
| --- | --- |
| 本次对话 | 用户描述的需求、贴出来的表格、明确的约束，直接使用，措辞可整理但技术名词照抄 |
| 附件（Excel、截图、旧文档） | 作为事实来源；解析后把关键内容写进数据 |
| 代码库 | 类名、接口名、表名、字段名、SQL 以代码为准；不确定的不要猜 |
| 模板自身 | 表头、章节标题、示例文字可以提示内容的写法 |
| 用户确认 | 前面都没有时，提问或标注【待确认】 |

## 4. 各类型字段的写法要求

| 字段类型 | 要求 |
| --- | --- |
| 名称、标题 | 与用户口径一致，不加工、不加"关于…的"这类前缀 |
| 短摘要 | 1–2 句，说明改了什么、为什么改，不写"旨在赋能"这类空话 |
| 长说明、背景 | 工程文档书面语，分点用 `1. 2. 3.` 或 `\n` 分行；先结论后细节 |
| 表格 | 每行一条记录，列名与表头一致；行数按真实内容，不凑数 |
| SQL | 原样保留（包括缩进和分号），多条用 `\n`；不自行改写表名/字段名 |
| 代码说明 | 每条一行，写清楚改了哪个类/方法、为什么 |
| 日期 | 用 `YYYY-MM-DD`；模板带格式时照常给这个格式 |
| 是否类 | 用 `true` / `false` |
| 人名、联系方式 | 只能来自上下文；没有就【待确认】，不要编 |

## 5. 自检

写完数据后运行：

```
python scripts/wf.py check 模板.docx 数据.json --config 字段配置.json
```

它会报告：缺键、空值、表格类型错误、表格行列与表头不匹配、配置里必填但数据为空、以及仍带【待确认】的字段。有 `[问题]` 就先修数据再生成。

## 6. 交付时要交代清楚

- 哪些字段直接来自上下文/附件/代码；
- 哪些是合理推断（说明推断依据）；
- 哪些是【待确认】占位，需要用户补什么；
- 数据 JSON 的保存位置，以及"改数据重新生成"的命令。
